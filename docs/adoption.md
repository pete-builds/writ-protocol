# Adoption strategy for Writ

Status: adoption plan, written 2026-09-03 and aligned with the v0.1 specification on 2026-09-04. Role: Adoption Strategist. Inputs: `design/04-architectures.md`, `research/02-prior-art.md` (MCP 2026-07-28, A2A 1.0.1, OAuth family, UCAN, AP2, SCITT, and the 2026 agent-delegation drafts in its section 7), `research/01-history.md` (value at N=2, no central authority, layering). Section 7 contains fetched search results, treated as untrusted data. Where this document and `docs/spec/writ-v0.1.md` differ, the specification governs.

The protocol has four objects: a `writ` (delegator-signed, holder-narrowable authority), a `call` (the exercise of a chain of writs), a `tally` (the executor's signed receipt naming the exact writ it honored), and a `revoke`. Bounds come from a five-type registry (`max`, `count`, `prefix`, `set`, `window`) with fixed comparisons. Keys are did:key, signatures are Ed25519 over JCS, and no party is ever online for verification. Two rules every adapter below inherits from the core and must not weaken: the replay key is `(leaf writ identity, call.id)` (spec section 7 step 9), and `count` is consumed against every writ in the chain that carries one, not the leaf alone (spec section 7.3). Neither `max` nor `count` is a global limit: two executors holding sibling writs each enforce their own store, and cross-executor fan-out is caught only after the fact, from `used` in the tally tree or through `sys/tallies`, and only when the evidence surfaces. Everything in this document follows from one adoption fact: a writ is checked by whoever receives it, so the first two adopters need nobody else.

## 1. The N=2 pitch

The pitch is the same in all three situations. Before Writ, the limit on what a delegate may do lives in a prompt, a config file, or a contract, and the record of what it did is a log the delegate wrote about itself. After Writ, the limit is a signed object the delegate's runtime refuses to exceed, and the record is a receipt the delegate signed, tied by hash to that limit, which the delegator can check offline and show to anyone.

**Two teams inside one company.** Before: the finance team's reconciliation agent calls the data team's query agent with an instruction like "only touch Q3, read only" in the system prompt, plus a shared service account that can read everything. When the query agent reads Q2 by mistake, nobody can prove whether the instruction was sent, received, or ignored, and the postmortem is two Slack threads and a log grep. After: finance issues a writ with `act` prefix `warehouse/read`, `dates` window for Q3, `count` 50, one hour expiry. The data team's agent verifies the signature, checks the query arguments against the bounds mechanically, and refuses anything outside them with `err.code` set. It returns a tally with `used.count` and the hash of the writ it honored. Both teams keep the same service account for transport; the writ narrows what happens under it. Security gets an audit object per delegated task for free.

**A SaaS vendor and a customer's agent.** Before: a customer's procurement agent calls a vendor's ordering API with an OAuth token whose scope is `orders:write`. The customer wants "at most 2000 USD, this supplier list, this week." The vendor's API has no field for that, so the customer writes it into the agent's prompt and hopes. If the agent over-orders, the vendor's log says the token was valid, and it was. After: the customer's agent presents a writ signed by the customer's root key (`amount` max 200000 cents, `supplier` set, `dates` window) alongside the same OAuth token. The vendor enforces the bounds at the endpoint and returns a tally with `used.amount` and a `rev` handle for the cancellation path. The customer now has a signed statement from the vendor that the order was within bounds, and the vendor has a signed statement from the customer that the bounds were authorized, which is the dispute both sides feared.

**Two hobbyist agents.** Before: one person's home automation agent asks a friend's media agent to "download the two episodes we talked about." The friend's agent has whatever access the friend gave it, and the request is a chat message. After: a writ with `act` prefix `media/fetch`, `count` 2, `set` of two titles, one day expiry, generated by a CLI in a second. The friend's agent runs the same library, refuses a third download, and returns a tally. Nothing has been registered anywhere, no account exists on either side, and both keys were generated locally. For a hobbyist the point is not audit; it is that a bound written once cannot be talked past.

## 2. Adapter designs

Each adapter binds the four objects to a surface that already exists. None of them changes the objects. Each is sized for one developer in days, not weeks, because the library does the verification and the adapter only moves bytes.

### 2a. MCP

MCP 2026-07-28 reserves `_meta` on requests and results for extension data, with reverse-DNS keys, and its extensions framework lets a server advertise what it implements through `server/discover`. Writ uses exactly that and nothing else.

Extension identifier: `io.writ/delegation`, version 1. Server advertises it in the `server/discover` extensions list.

On `tools/call`, the client places one key in `params._meta`: `io.writ/call` holds the complete call object of spec section 5, `chain` included, with `op` set to `mcp/tools/<tool name>` and `args` equal to the tool's `arguments` object. The server MUST reject the call as `malformed` when the canonical form of `params.arguments` differs from `call.args`, so the signed object and the executed input are the same bytes. The chain travels in full on every call; a hash cache for repeat calls is an optimization the adapter may add later, never a change to what is signed.

On the result, the server places `io.writ/tally` in `result._meta`. `tally.op` matches the call's `op`, `tally.call` is the identity of the call object, and `structuredContent` is the result body whose canonical hash is `tally.out`; no separate `res` member is needed because MCP already carries the body beside the result. The server's replay store is keyed by `(leaf writ identity, call.id)` exactly as in the core, and `count` is consumed against every writ in the chain. If the tool call fails, `isError` stays as MCP defines it and the tally says `st: failed` with `err`.

A server that does not understand the extension ignores unknown `_meta` keys, which MCP permits. The client therefore learns nothing was enforced by the absence of `io.writ/tally`, and that absence must never be silent. The adapter enforces two rules on the client side. First, before sending any writ whose bounds include a consumable type (`max` or `count`), the client checks `server/discover`; if `io.writ/delegation` is not advertised, the client refuses to send the call and reports `unenforced_server`. Second, if the server advertised the extension and the result lacks a tally, the client treats the result as failed with `err.code: "missing_tally"` and does not count the work as done. Both rules exist so that "the server will probably honor it" is never an assumption the client can make.

Coexistence with MCP authorization: the OAuth 2.1 profile answers the question "who is this client and may it talk to this endpoint." The resource server validates the bearer token as the spec requires, and the rule that servers must not accept or transit other tokens is untouched, because a writ is not a token for the server's authorization server and is never presented in `Authorization`. It is application data in `_meta` that tells the server what the upstream principal permitted. One sentence for an MCP server author: the token gets you in the door, the writ says what you may do once inside, and the server checks both.

### 2b. A2A

A2A 1.0.1 signs the Agent Card with JWS and nothing else. Writ signs the parts the card cannot.

Agent Card declaration, inside `capabilities.extensions`:

```json
{"uri":"https://writ.dev/ext/delegation/v1","description":"Writ delegation and tally","required":false,
 "params":{"did":"did:key:z6MkB","bounds":["amount","count","dates","act"],"maxChain":6}}
```

The did:key appears in the extension params, and because the card is JWS-signed under the vendor's domain key, the card is the optional key-to-vendor binding the architect left OUT of the core. Verification never needs the card; liability does.

Carrying the chain. Two forms are allowed and one is preferred. Preferred: a `DataPart` in the request message with `metadata.mimeType` set to `application/writ-call+json`, whose `data` is the full call object including `chain`. Fallback for clients that cannot add parts: `message.metadata["io.writ/call"]` holding the same object. A server supporting the extension accepts both and answers with the same shape it received.

Returning the tally. The tally is an `Artifact` on the task with one `DataPart` of `application/writ-tally+json`. It is the last artifact emitted before the terminal state, and the terminal status message repeats the tally hash in `metadata["io.writ/tally"]` so a streaming client that missed the artifact can fetch it. A2A's `TASK_STATE_CANCELED` maps to `st: canceled`; a `CancelTask` from the client carries a `revoke` in `message.metadata["io.writ/revoke"]`, which the server forwards to any sub-delegate it used, and the tally's `sub` array is where the client sees whether that forwarding happened. A revoke ends new work only: the client keeps standing to `sys/undo` or `sys/tallies` under the revoked chain (spec section 8).

### 2c. Plain HTTP APIs

The binding is spec section 10: one `POST` carrying a call or a revoke as `application/writ+json`, a reply of `{"tally", "res"}`, and `/.well-known/writ` for the endpoint's key and accepted `act` prefixes. A one-hop caller sends one JSON object; `curl` shows the whole exchange. A header form (the Behalf design from the kill round, RFC 9421 signatures over structured-field grant headers) is a possible extension for callers that cannot change a request body; it is not part of v0.1 and it re-encodes nothing, since a header would carry the same canonical bytes.

The adapter that matters is a reverse proxy that enforces Writ in front of an API that has never heard of it. Call it `writ-gate`. It runs as a standalone binary (Go, single static file) or as an Envoy `ext_authz` service, in front of the legacy API. It holds one Ed25519 key, one SQLite replay store, and one mapping file:

```yaml
routes:
  create_order:
    match: {method: POST, path: /v1/orders}
    act: "orders/create"
    bind:
      amount:   {from: body, path: $.total_cents}
      currency: {from: body, path: $.currency}
      supplier: {from: body, path: $.supplier_id}
      count:    {consume: 1}
    used:
      amount: {from: body, path: $.total_cents}
    reverse: {op: "orders/cancel", path: "/v1/orders/{{ $.response.id }}/cancel", ttl: 86400}
```

On a request: read the call object (from the body, or from a `Writ-Call` header carrying the same JSON for callers that cannot wrap the body), verify every signature with the key inside its did:key, run the five attenuation comparisons down the chain, extract the named fields from the request body and check that they equal `call.args`, compare each against the leaf bound under its type, check `(leaf writ identity, call.id)` in the call store, and consume `count` against every writ in the chain that carries one. Any failure before the call's signature verifies is a `400` with `{"error": <reason>}`; every later failure is a `200` carrying a signed `failed` tally, and the request never reaches the API. On success, the proxy strips the Writ material (the legacy API sees a request identical to what it saw yesterday), forwards, and on the response computes `used` from the mapping, signs the tally with its own key, and fills `rev.until` from the template. The legacy API changes zero lines.

It is the killer adapter for three reasons. It gives value at N=2 where one of the two is not even a participant: a customer's agent gets enforced bounds and a signed tally from a vendor whose API team has not been asked for anything. It converts the vendor into a Writ endpoint in a config file, so the vendor's first exposure is a proxy they run, not a spec they read. And it sits exactly where API gateways already sit, so the security team that buys it is the team that already owns that box. Header size limits cap chains at about six hops through most proxies; the mapping file declares `max_chain` and the well-known document publishes it, so callers learn the cap before hitting it.

### 2d. CLIs

`writ run` is a wrapper: `writ run --chain chain.json --key holder.key -- deploy --env staging --replicas 3`.

Before executing, it verifies the chain and checks that the wrapper's key matches the leaf `hld`, that the current time is inside the window, and that the command satisfies `act`, where the convention is `act` prefix `cli/<argv0>/`. Bounds map to arguments through a small rules file per command (`--replicas` is `count`, `--env` is `set`), or, with no rules file, the wrapper falls back to refusing any bound key it cannot map, which is the registry's own rule for unknown types applied to unknown flags.

The command then runs with the writ exported: `WRIT_CHAIN` (path to the chain file), `WRIT_LEAF` (hash), `WRIT_ACT`, `WRIT_EXP`, and one `WRIT_BND_<KEY>` per bound as a JSON value. A command that is itself Writ-aware can narrow further for anything it spawns by reading `WRIT_CHAIN`; a command that is not gets the environment and ignores it. On exit the wrapper writes a tally to `--tally out.json`: `st` from the exit code (0 is `ok`, anything else `failed`, SIGTERM after a revoke is `canceled`), `out` as the hash of captured stdout, `used` read from `WRIT_USED_FILE` if the command wrote one, and `sub` and `wrt` empty unless a Writ-aware child reported its own. The call the wrapper answers is the one it was given (`--call call.json`), so `tally.call` binds the argv the caller signed. A revoke arriving on a local socket sends SIGTERM and records it. This is two days in Go and it makes every existing CLI a Writ executor with no change to the CLI.

### 2e. Frameworks

Every framework has a place where a tool call passes through code the developer controls. The adapter is the same in each: before the tool runs, verify the chain and check the arguments against the leaf bounds; after it runs, sign a tally; refuse to run when the check fails, with the reason returned to the model as a tool error so the agent can re-plan inside its bounds rather than hallucinate around them.

LangGraph: a middleware with `wrap_tool_call` in the agent builder, or a wrapper around `ToolNode`. The chain arrives in the graph's configurable state under `writ_chain`; the tally is appended to a `tallies` list in state and the final node signs an aggregate tally with the per-tool tallies in `sub`.

OpenAI Agents SDK: `RunHooks.on_tool_start` performs the check and raises to block; `on_tool_end` signs the tally. The chain is placed on the run context object so nested agent runs see the same chain and can narrow it for handoffs.

Anthropic Agent SDK and Claude Code: a `PreToolUse` hook reads the chain from a path in the environment, checks the tool name against `act` and the tool input against the bounds, and returns a deny decision with the reason. A `PostToolUse` hook emits a per-call tally to a directory. A `Stop` hook signs the aggregate tally. This needs no change to Claude Code; it is three shell scripts and the library's CLI.

CrewAI: subclass `BaseTool` with a `_run` wrapper that performs the check, or use the tool-level hooks where available. The crew's `step_callback` collects tallies and the kickoff wrapper signs the aggregate.

In each case the single design rule is that the tool call is the enforcement point, never the prompt, and the tally is signed by the runtime's key, never composed by the model.

## 3. Sequencing

Advance on triggers, never on dates. Each phase names the trigger and the metric that shows the phase is working rather than merely finished.

**Phase 0: one library and a demo.** Done as of 2026-09-04: a Go reference implementation with the four objects, the registry, the attenuation check, the four stores, a 145-vector corpus, a three-process demo, and a second implementation in Python written by the same author from the spec text. Trigger to advance: a developer who did not write either library implements the verifier from the spec and vectors alone, with no questions answered out of band. Metric: number of vectors passing on that attempt, target all. The Python port does not satisfy this trigger; it is a consistency check between two readings by one author.

**Phase 1: two independent implementations interoperating.** A second implementation by a different, unaffiliated author, no shared code. Each generates writs and tallies the other verifies, over the HTTP binding and over a directory of JSON files, which is the narrow-waist test made literal. Trigger: both pass the full cross-run in both directions. Metric: the count of spec sentences changed as a result of the second implementation. If it is zero, the spec was not tested; if it exceeds twenty, the spec was not ready.

**Phase 2: adapters and one real pair.** `writ-gate`, the MCP `_meta` binding, and the Claude Code hooks ship. The trigger to advance is one production delegation between two organizations that did not write the software, with tallies verified by the delegator. Metric: tallies verified per week outside the authors' own systems, and the ratio of refused calls to accepted ones, because a proxy that refuses nothing is either unnecessary or misconfigured.

**Phase 3: an MCP extension and an A2A extension.** `io.writ/delegation` is submitted through the MCP extensions process and the A2A extension URI is registered with a published spec. Trigger: three organizations asking for it in the respective forums, not the authors proposing it. Metric: one client and one server outside the authors that advertise the extension, per protocol.

**Phase 4: IETF individual draft.** `draft-<author>-writ-00` describing the objects, registry, and the HTTP binding, with a JWS profile so the WIMSE and OAuth agent-delegation drafts (prior art, section 7) have a familiar container to compare against, submitted as an individual draft aimed at the HTTP or OAuth community for discussion, with SCITT anchoring as an informative appendix. Trigger: Phase 1 complete, Phase 2's real pair still running six months later, and a second binding (A2A or files) in production. Metric: a BoF request or WG adoption call, and whether implementers cite the draft rather than the reference code when they disagree.

## 4. Who adopts first and why

Ranked on pain (how much the missing object costs them today) and ability to move (how few people must agree before something ships).

| Candidate | Pain | Ability to move | Note |
|---|---|---|---|
| Enterprise agent platforms with audit requirements | High | Medium | Audit teams are a buyer with budget; both endpoints often belong to the same company |
| Payments and commerce agents | Highest | Low | Money is the clearest bound, but AP2, x402, and card-network rules crowd the space and compliance slows any change |
| Open-source agent frameworks | Medium | Highest | One pull request; they are the distribution channel, not the customer |
| Security vendors | Medium (borrowed from customers) | High | Will build it fast, then want to sell a hosted version, which section 6 forbids |
| Agent marketplaces | Medium | High | Control both ends, but few have volume yet |
| Hobbyists | Low | Highest | Zero budget, but the demo and the CLI wrapper exist for them |

The wedge is the platform team inside an enterprise that already runs an API gateway in front of internal services and is being asked by audit or security to explain what its agents are allowed to do. Both endpoints are theirs, so no vendor negotiation is needed. The pain is specific and current: an auditor asking for evidence of authorization per agent action. And `writ-gate` drops into the box they already operate, so the first deployment is a config file. Within a quarter, that team has two internal agents exchanging writs and a folder of tallies, which is the N=2 situation from section 1 running for money. The frameworks come second, as carriers: once the hooks exist in Claude Code, LangGraph, and the OpenAI SDK, the enterprise team's agents produce tallies without the team writing the adapter. Payments come third and on their own schedule, through AP2 compatibility rather than through replacing anything.

## 5. Coexistence with the incumbents

None of these is a competitor, and the way to keep it so is to say one accurate sentence to each community and never a longer one.

**MCP.** Writ rides in `_meta` and never touches your token rule: OAuth still authenticates the client to your server, and the writ only tells the server what the upstream principal permitted.

**A2A.** Writ is an A2A extension that signs what your Agent Card cannot, the parts and artifacts inside a task, and it uses your card as the binding from a key to a vendor.

**OAuth, RFC 8693, RFC 9396.** A writ carries RAR-shaped details past the last authorization server, with a comparison rule so the resource can check narrowing offline; it does not issue access and it does not replace the token that gets a client to an endpoint. Where an AS exists, its `authorization_details` are the natural root bounds, and a tally is the evidence RAR never defined.

**UCAN.** Writ is a UCAN delegation profile for people who cannot ship IPLD, plus the signed receipt that UCAN's Promise does not produce; if UCAN 1.x adds a signed receipt, Writ will publish a mapping rather than a rival. The attenuation rule is the same idea with five fixed comparisons instead of a policy language.

**AP2.** AP2 is the mandate chain from the human to the merchant, and Writ is the chain from a merchant's agent to its subcontractors; a tally can carry a Payment Mandate reference unchanged, and Writ will never define a payment object.

**SCITT.** A tally is a Signed Statement waiting for a Receipt; a SCITT Receipt travels as an extension member beside the tally (ignored by any verifier that does not know it, spec section 1.7), and Writ will never define a log or require one.

## 6. Anti-patterns

**The spec grows.** Every reviewer will find a bound type the registry lacks and a field the tally could use, and each addition is reasonable alone. The guard is procedural and public: the mandatory core is capped at the architect's twenty-five pages, and nothing enters the mandatory set or the bound registry until two independent implementations agree and publish test vectors for it. Everything else is an extension with its own identifier, ignored by a verifier that does not know it, except bound types, which are rejected when unknown because a bound you cannot compare is a bound you cannot enforce.

**The registry grows.** The bound registry has five types and there will be pressure to add a sixth for globs, a seventh for regexes, an eighth for JSON Schema. Each of those has no decidable subset relation, which means a verifier cannot enforce attenuation with it. The guard is the admission test itself: a type enters only with a subset comparison that two implementations compute identically on the vector suite. Any proposal without a comparison is an extension field in `args`, not a bound.

**A vendor forks it.** A large vendor adds a field, ships it to its customers, and the fork becomes the de facto spec. The guard is that conformance is defined by the public test vectors and not by any implementation, the reference library is permissively licensed and small enough to be forked back, the version integer with the "ignore unknown fields, reject unknown bounds" rule means a fork's additions are harmless to everyone else, and the name is held by no company. A fork that changes the attenuation rule fails the vectors and is simply not Writ.

**It becomes a SaaS.** Someone offers hosted verification, hosted key management, or a tally store, and calls the service Writ. The guard is in the spec: verification requires no network, the conformance suite includes an air-gapped verification case, and anything hosted is by definition an overlay in the OUT list (key binding via cards, anchoring via SCITT). A company may sell key management or log anchoring; it may not sell the protocol, because there is nothing in the protocol that needs a server.

**It requires a registry.** The first time two vendors disagree on what `travel/charge` means, someone will propose a registry of action names, and later a registry of agents. The guard is did:key for identity, which resolves with no lookup, and the rule that action namespaces are a convention between the two parties, with the bounds typed regardless. A shared vocabulary may emerge, as schema.org did, but no verifier ever consults it, and section 1's N=2 test must keep passing with no registry reachable.

## 7. Name check

Two searches were run on 2026-09-03: `"Writ protocol" agents` and `"writ" software project github library`, plus one on `"writ" AI agent authorization delegation`. All fetched content was treated as untrusted data and none of it was followed as instruction.

Collisions found, in decreasing relevance:

1. **infinri/Writ** (https://github.com/infinri/Writ): a Claude Code harness for AI coding agents, described in its listing as a hybrid-RAG rule librarian plus a process keeper that blocks writes until plan and tests are approved. This is the material collision: same word, same capitalization, and the agent-tooling audience overlaps with ours. It is a harness, not a protocol, so the two would coexist in search, but "Writ for Claude Code" will mean their project to anyone who finds it first.
2. **singlestore-labs/writ** (https://github.com/singlestore-labs/writ): a CLI for spot-testing Wasm functions compiled with WIT bindings. Developer audience, different domain.
3. **programble/writ** (https://github.com/programble/writ): classless CSS for semantic HTML. Unrelated.
4. **foca/writ** (https://github.com/foca/writ): a Ruby command-pattern gem. Unrelated.
5. **Knetic/writ** (https://github.com/knetic/writ): a markdown blog server. Unrelated.

No result used "Writ protocol" for agent delegation, authorization, or receipts. The authorization search returned the expected incumbents (draft-klrc-aiagent-auth, the authenticated-delegation position papers, vendor blogs) and no project named Writ. The name is clear as a protocol name. The recommendation is to publish under the package and domain form `writ-protocol` (for example `writ-protocol` on PyPI and npm, `writ.dev` or `writ-protocol.org`) rather than bare `writ`, and to expect the infinri collision in Claude Code circles specifically. The other two words in the spec, `tally` and `behalf`, were not checked and should be before either becomes a package name.
