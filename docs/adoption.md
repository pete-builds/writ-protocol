# How Writ could be adopted

Status: adoption plan, written 2026-09-03 and aligned with the v0.1 specification on 2026-09-04; rewritten for readability on 2026-09-28 with no change of substance. Role: Adoption Strategist. Inputs: `design/04-architectures.md`, `research/02-prior-art.md` (MCP 2026-07-28, A2A 1.0.1, the OAuth family, UCAN, AP2, SCITT, and the 2026 agent-delegation drafts in its section 7), and `research/01-history.md` (value with two parties, no central authority, layering). Section 7 contains fetched search results, treated as untrusted data. Where this document and `docs/spec/writ-v0.1.md` differ, the specification governs.

## The short version

Writ has five signed objects:

- a `writ`, authority signed by the delegator, which the holder can narrow;
- a `call`, which exercises a chain of writs;
- a `tally`, the executor's signed receipt naming the exact writ it honored;
- a `revoke`, which withdraws a writ;
- an `ack`, an executor's signed record of when it recorded a revoke and which work under the writ it held then.

Limits come from five bound types with fixed comparison rules (`max`, `count`, `prefix`, `set`, `window`). Keys are did:key, signatures are Ed25519 over canonical JSON (JCS), and no party ever has to be online for anyone to verify anything.

Every adapter below inherits two rules from the core and must not weaken them:

1. **The replay key is `(leaf writ identity, call.id)`** (spec section 7 step 9). A retried call is answered with its stored tally; it never runs twice.
2. **`count` is consumed against every writ in the chain that carries one**, not only the last writ (spec section 7.3), so re-delegating to yourself resets nothing.

Neither `max` nor `count` is a global limit. Two executors holding sibling writs each enforce their own store, and fan-out across executors is caught only after the fact, from `used` in the tally tree or through `sys/tallies`, and only when the evidence surfaces.

Everything else here follows from one fact: **a writ is checked by whoever receives it, so the first two adopters need nobody else.**

## 1. The pitch, with two parties

The pitch is the same in every setting. Today, the limit on what a delegate may do lives in a prompt, a config file, or a contract, and the record of what it did is a log the delegate wrote about itself. With Writ, the limit is a signed object the delegate's runtime refuses to exceed, and the record is a receipt the delegate signed, tied by hash to that limit, which the delegator can check offline and show to anyone.

**Two teams inside one company.**

- *Today:* the finance team's reconciliation agent calls the data team's query agent. The system prompt says something like "only touch Q3, read only", and a shared service account can read everything. When the query agent reads Q2 by mistake, nobody can prove whether the instruction was sent, received, or ignored. The postmortem is two Slack threads and a log grep.
- *With Writ:* finance issues a writ: `act` prefix `warehouse/read`, a `dates` window covering Q3, `count` 50, one-hour expiry. The data team's agent verifies the signature, checks the query's arguments against the bounds mechanically, and refuses anything outside them with `err.code` set. It returns a tally with `used.count` and the hash of the writ it honored. Both teams keep the same service account for transport; the writ narrows what happens under it. Security gets an audit object for every delegated task, at no extra cost.

**A SaaS vendor and a customer's agent.**

- *Today:* a customer's procurement agent calls a vendor's ordering API with an OAuth token scoped `orders:write`. The customer wants "at most 2000 USD, these suppliers, this week", but the API has no field for that, so the customer writes it into the agent's prompt and hopes. If the agent over-orders, the vendor's log says the token was valid, and it was.
- *With Writ:* the agent presents a writ signed by the customer's root key (`amount` max 200000 cents, a `supplier` set, a `dates` window) alongside the same OAuth token. The vendor enforces the bounds at the endpoint and returns a tally with `used.amount` and a `rev` handle for cancelling. The customer now holds a signed statement from the vendor that the order was within bounds, and the vendor holds a signed statement from the customer that those bounds were authorized. That settles the dispute each side feared.

**Two hobbyist agents.**

- *Today:* one person's home automation agent asks a friend's media agent to "download the two episodes we talked about". The friend's agent has whatever access the friend gave it, and the request is a chat message.
- *With Writ:* a writ with `act` prefix `media/fetch`, `count` 2, a `set` of two titles, and a one-day expiry, generated by a CLI in a second. The friend's agent runs the same library, refuses a third download, and returns a tally. Nothing is registered anywhere, neither side has an account, and both keys were generated locally. For a hobbyist the point is not audit; it is that a limit written once cannot be talked past.

## 2. Adapters

Each adapter carries the four objects over a surface that already exists, and none of them changes the objects. Each is sized for one developer in days, not weeks, because the library does the verification and the adapter only moves bytes.

### 2a. MCP

MCP 2026-07-28 reserves `_meta` on requests and results for extension data, with reverse-DNS keys, and its extensions framework lets a server advertise what it implements through `server/discover`. Writ uses exactly that and nothing else.

- **Identifier.** The extension is `io.writ/delegation`, version 1. A server advertises it in the `server/discover` extensions list.
- **The call.** On `tools/call`, the client puts one key in `params._meta`: `io.writ/call`, holding the complete call object of spec section 5, `chain` included, with `op` set to `mcp/tools/<tool name>` and `args` equal to the tool's `arguments` object. The server MUST reject the call as `malformed` when the canonical form of `params.arguments` differs from `call.args`, so that what was signed and what runs are the same bytes. The chain travels in full on every call; caching it by hash for repeat calls is an optimization an adapter may add later, never a change to what is signed.
- **The tally.** On the result, the server puts `io.writ/tally` in `result._meta`. `tally.op` matches the call's `op`, `tally.call` is the identity of the call object, and `structuredContent` is the result body whose canonical hash is `tally.out`. No separate `res` member is needed, because MCP already carries the body beside the result. The server's replay store is keyed by `(leaf writ identity, call.id)` exactly as in the core, and `count` is consumed against every writ in the chain. `isError` is `true` exactly when the tally's `st` is not `ok`, so a tool failure is `isError: true` with a tally saying `st: failed` and `err`. Nothing signs `content`: a client checks the tally, the body, and `isError` against each other, and shows a result rebuilt from those, never the server's `content` (docs/bindings.md).

A server that does not understand the extension ignores unknown `_meta` keys, which MCP permits. So the only sign that nothing was enforced is a missing `io.writ/tally`, and that must never pass silently. The client adapter enforces two rules:

1. Before sending any writ whose bounds include a consumable type (`max` or `count`), the client checks `server/discover`. If `io.writ/delegation` is not advertised, it refuses to send the call and reports `unenforced_server`.
2. If the server advertised the extension and the result has no tally, the client treats the result as failed with `err.code: "missing_tally"` and does not count the work as done.

Both rules exist so that "the server will probably honor it" is never an assumption the client can make.

*Built 2026-09-30 as `impl/go/mcpbind` and the stdio server `cmd/writ-mcp`; docs/bindings.md says what was tested.*

**Living with MCP authorization.** The OAuth 2.1 profile answers "who is this client, and may it talk to this endpoint?" The resource server validates the bearer token as the spec requires. The rule that servers must not accept or pass along other tokens is untouched, because a writ is not a token for the server's authorization server and never appears in `Authorization`. It is application data in `_meta` that tells the server what the upstream principal permitted. In one sentence for an MCP server author: the token gets you in the door, the writ says what you may do once inside, and the server checks both.

### 2b. A2A

A2A 1.0.1 signs the Agent Card with JWS and nothing else. Writ signs the parts the card cannot.

The Agent Card declares the extension inside `capabilities.extensions`:

```json
{"uri":"https://writ.dev/ext/delegation/v1","description":"Writ delegation and tally","required":false,
 "params":{"did":"did:key:z6MkB","bounds":["amount","count","dates","act"],"maxChain":6}}
```

The did:key appears in the extension's params. Because the card is JWS-signed under the vendor's domain key, the card becomes the optional binding from a key to a vendor that the architecture deliberately left out of the core. Verification never needs the card; liability does.

- **Carrying the chain.** Two forms are allowed, and one is preferred. Preferred: a `DataPart` in the request message with `metadata.mimeType` set to `application/writ-call+json`, whose `data` is the full call object including `chain`. For clients that cannot add parts: `message.metadata["io.writ/call"]`, holding the same object. A server that supports the extension accepts both and answers in the shape it received.
- **Returning the tally.** The tally is an `Artifact` on the task with one `DataPart` of `application/writ-tally+json`. It is the last artifact emitted before the terminal state, and the terminal status message repeats the tally's hash in `metadata["io.writ/tally"]`, so a streaming client that missed the artifact can fetch it.
*Message-level helpers built 2026-09-30 as `impl/go/a2abind` (docs/bindings.md); not yet run against an A2A SDK.*

- **Cancelling.** A2A's `TASK_STATE_CANCELED` maps to `st: canceled`. A `CancelTask` from the client carries a `revoke` in `message.metadata["io.writ/revoke"]`, which the server forwards to any sub-delegate it used; the tally's `sub` array shows the client whether that forwarding happened. A revoke ends new work only: the client keeps its standing to send `sys/undo` or `sys/tallies` under the revoked chain (spec section 8).

### 2c. Plain HTTP APIs

The binding is spec section 10: one `POST` carrying a call or a revoke as `application/writ+json`, a reply of `{"tally", "res"}`, and `/.well-known/writ` for the endpoint's key and the `act` prefixes it accepts. A one-hop caller sends one JSON object, and `curl` shows the whole exchange. A header form (the Behalf design from the kill round, RFC 9421 signatures over structured-field grant headers) is a possible extension for callers that cannot change a request body. It is not part of v0.1, and it would re-encode nothing, since a header would carry the same canonical bytes.

**The adapter that matters most is a reverse proxy** that enforces Writ in front of an API that has never heard of it. Call it `writ-gate`. It runs as a standalone binary (Go, one static file) or as an Envoy `ext_authz` service in front of the legacy API. It holds one Ed25519 key, one SQLite replay store, and one mapping file:

```yaml
routes:
  create_order:
    match: {method: POST, path: /v1/orders}
    act: "orders/create"
    bind:
      amount:   {from: body, path: $.total_cents}
      currency: {from: body, path: $.currency}
      supplier: {from: body, path: $.supplier_id}
      count:    {consume: 1}
    used:
      amount: {from: body, path: $.total_cents}
    reverse: {op: "orders/cancel", path: "/v1/orders/{{ $.response.id }}/cancel", ttl: 86400}
```

On each request, the proxy:

1. reads the call object, from the body or from a `Writ-Call` header carrying the same JSON for callers that cannot wrap the body;
2. verifies every signature with the key inside its did:key;
3. runs the attenuation comparisons down the chain;
4. extracts the named fields from the request body, checks that they equal `call.args`, and compares each against the last writ's bound of that type;
5. looks up `(leaf writ identity, call.id)` in the call store;
6. consumes `count` against every writ in the chain that carries one.

A failure before the call's signature verifies is a `400` with `{"error": <reason>}`. Every later failure is a `200` carrying a signed `failed` tally, and the request never reaches the API. On success, the proxy forwards a request rebuilt from the signed values alone, so the legacy API sees the request it saw yesterday, minus anything the call did not sign. Forwarding the caller's own bytes would let the proxy check one reading of a body while the API executes another (a case-folded duplicate member, trailing JSON, a query parameter that overrides the body). On the response, it computes `used` from the mapping, signs the tally with its own key, and fills `rev.until` from the template. The legacy API changes zero lines.

*Built 2026-09-30 as `cmd/writ-gate` (docs/writ-gate.md), with a JSON mapping and the reference file store in place of YAML and SQLite, and the call in the `Writ-Call` header only. Each route is a strict request contract: the body holds exactly the bound members, every path parameter is bound, and there is no query string.*

It is the adapter that matters most, for three reasons:

- **It gives value with two parties even when one of them is not participating.** A customer's agent gets enforced bounds and a signed tally from a vendor whose API team has not been asked for anything.
- **It turns the vendor into a Writ endpoint with a config file.** The vendor's first exposure is a proxy they run, not a spec they read.
- **It sits where API gateways already sit.** The security team that buys it is the team that already owns that box.

Header size limits cap chains at about six hops through most proxies. The mapping file declares `max_chain` and the well-known document publishes it, so callers learn the cap before they hit it.

### 2d. CLIs

`writ run` wraps any command: `writ run --chain chain.json --key holder.key -- deploy --env staging --replicas 3`.

**Before running**, it verifies the chain and checks that the wrapper's key matches the last writ's `hld`, that the current time is inside the window, and that the command satisfies `act`, by the convention that `act` is a prefix of the form `cli/<argv0>/`. Bounds map to arguments through a small rules file per command (`--replicas` is `count`, `--env` is `set`). With no rules file, the wrapper refuses any bound it cannot map, which applies the registry's rule for unknown types to unknown flags.

**While it runs**, the command sees the writ in its environment: `WRIT_CHAIN` (path to the chain file), `WRIT_LEAF` (hash), `WRIT_ACT`, `WRIT_EXP`, and one `WRIT_BND_<KEY>` per bound as a JSON value. A command that is itself Writ-aware can narrow further for anything it spawns by reading `WRIT_CHAIN`; a command that is not simply ignores the environment.

**On exit**, the wrapper writes a tally to `--tally out.json`:

- `st` from the exit code: 0 is `ok`, anything else `failed`, and SIGTERM after a revoke is `canceled`;
- `out` as the hash of captured stdout;
- `used` read from `WRIT_USED_FILE`, if the command wrote one;
- `sub` and `wrt` empty unless a Writ-aware child reported its own.

The call the wrapper answers is the one it was given (`--call call.json`), so `tally.call` binds the argv the caller signed. A revoke arriving on a local socket sends SIGTERM and records it. This is two days of work in Go, and it makes every existing CLI a Writ executor with no change to the CLI.

### 2e. Agent frameworks

Every framework has a place where a tool call passes through code the developer controls. The adapter is the same in each: before the tool runs, verify the chain and check the arguments against the last writ's bounds; after it runs, sign a tally; when the check fails, refuse to run and return the reason to the model as a tool error, so the agent can re-plan inside its bounds rather than hallucinate around them.

- **LangGraph:** a middleware with `wrap_tool_call` in the agent builder, or a wrapper around `ToolNode`. The chain arrives in the graph's configurable state under `writ_chain`. Each tally is appended to a `tallies` list in state, and the final node signs an aggregate tally with the per-tool tallies in `sub`.
- **OpenAI Agents SDK:** `RunHooks.on_tool_start` performs the check and raises to block; `on_tool_end` signs the tally. The chain is placed on the run context object, so nested agent runs see the same chain and can narrow it for handoffs.
- **Anthropic Agent SDK and Claude Code:** a `PreToolUse` hook reads the chain from a path in the environment, checks the tool name against `act` and the tool input against the bounds, and returns a deny decision with the reason. A `PostToolUse` hook writes a per-call tally to a directory, and a `Stop` hook signs the aggregate tally. This needs no change to Claude Code: it is three shell scripts and the library's CLI. *Shipped 2026-09-30, ahead of the sequencing below, as `cmd/writ-hook` (docs/claude-code.md): a Go program rather than shell scripts, with a per-call receipt and no aggregate tally yet.*
- **CrewAI:** subclass `BaseTool` with a `_run` wrapper that performs the check, or use the tool-level hooks where available. The crew's `step_callback` collects tallies, and the kickoff wrapper signs the aggregate.

In every case the one design rule is the same: the tool call is the enforcement point, never the prompt, and the tally is signed by the runtime's key, never composed by the model.

## 3. Sequencing

Move to the next phase on a trigger, never on a date. Each phase names the trigger, and the metric that shows it is working rather than merely finished.

**Phase 0: one library and a demo.** Done as of 2026-09-04: a Go reference implementation with the four objects, the bound registry, the attenuation check, the four stores, a 145-vector corpus, a three-process demo, and a second implementation in Python written by the same author from the spec text. (By 2026-09-28 the corpus had grown to 209 vectors and 20 executor scenarios, the spec had named a fifth store for reversals, and the Python implementation had gained an executor.)
- *Trigger:* a developer who wrote neither library implements the verifier from the spec and vectors alone, with no questions answered out of band.
- *Metric:* the number of vectors passing on that attempt; the target is all of them. The Python port does not satisfy this trigger. It checks that one author reads the spec the same way twice.

**Phase 1: two independent implementations that interoperate.** A second implementation by a different, unaffiliated author, sharing no code. Each generates writs and tallies the other verifies, over the HTTP binding and over a directory of JSON files, which tests literally that Writ does not depend on its transport.
- *Trigger:* both pass the full cross-run in both directions.
- *Metric:* the number of spec sentences changed because of the second implementation. Zero means the spec was not tested; more than twenty means it was not ready.

**Phase 2: adapters and one real pair.** `writ-gate`, the MCP `_meta` binding, and the Claude Code hooks ship.
- *Trigger:* one production delegation between two organizations that did not write the software, with the tallies verified by the delegator.
- *Metrics:* tallies verified per week outside the authors' own systems, and the ratio of refused calls to accepted ones, because a proxy that refuses nothing is either unnecessary or misconfigured.

**Phase 3: an MCP extension and an A2A extension.** `io.writ/delegation` is submitted through the MCP extensions process, and the A2A extension URI is registered with a published spec.
- *Trigger:* three organizations asking for it in those forums, not the authors proposing it.
- *Metric:* one client and one server outside the authors advertising the extension, for each protocol.

**Phase 4: an IETF individual draft.** `draft-<author>-writ-00`, describing the objects, the registry, and the HTTP binding, with a JWS profile so the WIMSE and OAuth agent-delegation drafts (prior art, section 7) have a familiar container to compare against. It is submitted as an individual draft aimed at the HTTP or OAuth community for discussion, with SCITT anchoring as an informative appendix.
- *Trigger:* Phase 1 complete, Phase 2's real pair still running six months later, and a second binding (A2A or files) in production.
- *Metrics:* a BoF request or a working-group adoption call, and whether implementers cite the draft rather than the reference code when they disagree.

## 4. Who adopts first, and why

Candidates, ranked on pain (how much the missing object costs them today) and ability to move (how few people must agree before something ships):

| Candidate | Pain | Ability to move | Note |
|---|---|---|---|
| Enterprise agent platforms with audit requirements | High | Medium | Audit teams are a buyer with budget; both endpoints often belong to the same company |
| Payments and commerce agents | Highest | Low | Money is the clearest bound, but AP2, x402, and card-network rules crowd the space and compliance slows any change |
| Open-source agent frameworks | Medium | Highest | One pull request; they are the distribution channel, not the customer |
| Security vendors | Medium (borrowed from customers) | High | Will build it fast, then want to sell a hosted version, which section 6 forbids |
| Agent marketplaces | Medium | High | Control both ends, but few have volume yet |
| Hobbyists | Low | Highest | Zero budget, but the demo and the CLI wrapper exist for them |

**The first adopter is the platform team inside an enterprise** that already runs an API gateway in front of internal services and is being asked by audit or security to explain what its agents are allowed to do.

- Both endpoints are theirs, so no vendor negotiation is needed.
- The pain is specific and current: an auditor asking for evidence of authorization for each agent action.
- `writ-gate` drops into the box they already operate, so the first deployment is a config file.

Within a quarter, that team has two internal agents exchanging writs and a folder of tallies: the two-party situation from section 1, running for real. Frameworks come second, as carriers. Once the hooks exist in Claude Code, LangGraph, and the OpenAI SDK, the enterprise team's agents produce tallies without the team writing an adapter. Payments come third and on their own schedule, through compatibility with AP2 rather than by replacing anything.

## 5. Living with the incumbents

None of these is a competitor. The way to keep it so is to say one accurate sentence to each community, and never a longer one.

**MCP.** Writ rides in `_meta` and never touches your token rule: OAuth still authenticates the client to your server, and the writ only tells the server what the upstream principal permitted.

**A2A.** Writ is an A2A extension that signs what your Agent Card cannot, the parts and artifacts inside a task, and it uses your card as the binding from a key to a vendor.

**OAuth, RFC 8693, RFC 9396.** A writ carries RAR-shaped details past the last authorization server, with a comparison rule so the resource can check narrowing offline. It does not grant access, and it does not replace the token that gets a client to an endpoint. Where an authorization server exists, its `authorization_details` are the natural root bounds, and a tally is the evidence RAR never defined.

**UCAN.** Writ is a UCAN delegation profile for people who cannot ship IPLD, plus a receipt tree. UCAN already specifies a signed Receipt for an invocation, and ucanto runs it in production; an earlier version of this paragraph said UCAN had only a Promise, which was wrong (corrected 2026-09-29). What a tally adds is the tallies of the work delegated below it, embedded verbatim, with consumption accounted across them, and standing recovery and reversal by any upstream issuer. Writ should publish a mapping from a tally to a UCAN Receipt rather than present itself as a rival. The attenuation rule is the same idea, with five fixed comparisons instead of a policy language.

**Tenuo.** Tenuo ships task-scoped warrants that narrow at every hop, checked offline at the tool boundary, with MCP middleware and opt-in signed receipts of each authorization decision. For a team that needs only request-time narrowing inside its own deployment, Tenuo or gateway policy plus ordinary logs is the simpler choice. Writ's case rests on what comes back after the work: the receipt tree, the accounting across it, and recovery after expiry. Swapping test vectors with Tenuo is worth offering before claiming any difference.

**AP2.** AP2 is the mandate chain from the human to the merchant, and Writ is the chain from a merchant's agent to its subcontractors. A tally can carry a Payment Mandate reference unchanged, and Writ will never define a payment object.

**SCITT.** A tally is a Signed Statement waiting for a Receipt. A SCITT Receipt travels as an extension member beside the tally (ignored by any verifier that does not know it, spec section 1.7), and Writ will never define a log or require one.

## 6. How it could go wrong, and the guard for each

**The spec grows.** Every reviewer will find a bound type the registry lacks and a field the tally could use, and each addition is reasonable on its own. The guard is procedural and public. The mandatory core is capped at the architect's twenty-five pages, and nothing enters the mandatory set or the bound registry until two independent implementations agree and publish test vectors for it. Everything else is an extension with its own identifier, ignored by a verifier that does not know it. The exception is bound types, which are rejected when unknown, because a bound you cannot compare is a bound you cannot enforce.

**The registry grows.** The registry has five types, and there will be pressure to add a sixth for globs, a seventh for regexes, an eighth for JSON Schema. None of those has a decidable subset relation, which means a verifier could not enforce narrowing with them. The guard is the admission test itself: a type enters only with a subset comparison that two implementations compute identically on the vector suite. A proposal without one is an extension field in `args`, not a bound.

**A vendor forks it.** A large vendor adds a field, ships it to its customers, and the fork becomes the de facto spec. The guards:

- Conformance is defined by the public test vectors, not by any implementation.
- The reference library is permissively licensed, and small enough to fork back.
- The version integer and the rule "ignore unknown fields, reject unknown bounds" make a fork's additions harmless to everyone else.
- No company holds the name.

A fork that changes the attenuation rule fails the vectors, and is simply not Writ.

**It becomes a SaaS.** Someone offers hosted verification, hosted key management, or a tally store, and calls the service Writ. The guard is in the spec: verification needs no network, the conformance suite includes an air-gapped verification case, and anything hosted is by definition an overlay the architecture left out (key binding through cards, anchoring through SCITT). A company may sell key management or log anchoring; it cannot sell the protocol, because nothing in the protocol needs a server.

**It requires a registry.** The first time two vendors disagree on what `travel/charge` means, someone will propose a registry of action names, and later a registry of agents. The guard is did:key for identity, which resolves with no lookup, and the rule that action names are a convention between the two parties, with the bounds typed regardless. A shared vocabulary may emerge, as schema.org did, but no verifier ever consults it, and section 1's two-party test must keep passing with no registry reachable.

## 7. Name check

Two searches were run on 2026-09-03, `"Writ protocol" agents` and `"writ" software project github library`, plus one on `"writ" AI agent authorization delegation`. All fetched content was treated as untrusted data, and none of it was followed as an instruction.

Collisions found, most relevant first:

1. **infinri/Writ** (https://github.com/infinri/Writ): a Claude Code harness for AI coding agents, described in its listing as a hybrid-RAG rule librarian plus a process keeper that blocks writes until the plan and tests are approved. This is the collision that matters: same word, same capitalization, and an overlapping audience in agent tooling. It is a harness, not a protocol, so the two would coexist in search, but "Writ for Claude Code" will mean their project to anyone who finds it first.
2. **singlestore-labs/writ** (https://github.com/singlestore-labs/writ): a CLI for spot-testing Wasm functions compiled with WIT bindings. A developer audience, in a different domain.
3. **programble/writ** (https://github.com/programble/writ): classless CSS for semantic HTML. Unrelated.
4. **foca/writ** (https://github.com/foca/writ): a Ruby command-pattern gem. Unrelated.
5. **Knetic/writ** (https://github.com/knetic/writ): a markdown blog server. Unrelated.

No result used "Writ protocol" for agent delegation, authorization, or receipts. The authorization search returned the expected incumbents (draft-klrc-aiagent-auth, the authenticated-delegation position papers, vendor blogs) and no project named Writ. The name is clear as a protocol name.

The recommendation is to publish under the package and domain form `writ-protocol` (for example `writ-protocol` on PyPI and npm, and `writ.dev` or `writ-protocol.org`) rather than bare `writ`, and to expect the infinri collision in Claude Code circles specifically. The spec's two other words, `tally` and `behalf`, were not checked, and should be before either becomes a package name.
