# Writ and x402: who may make the agent pay

x402 lets a client pay for an HTTP resource. The server answers `402 Payment Required` with a list of acceptable payments, the client signs an authorization for one of them, and a facilitator settles it on chain. The x402 v2 specification ([coinbase/x402, `specs/x402-specification-v2.md`](https://github.com/coinbase/x402/blob/main/specs/x402-specification-v2.md)) says plainly what it leaves out: its "Out of Scope" list names client-side budget management and session handling.

That is the gap this page fills with Writ. x402 answers "is this payment valid?" Writ answers "was this agent allowed to ask for it, within which limits, and what did the signer do?" Nothing here changes x402 or adds a payment object to Writ (adoption.md: Writ will never define one). It is a binding: which call arguments carry which x402 fields, and which bounds limit them.

## The shape

The agent never holds the payment key. The signer does, and the signer is the Writ executor.

1. The agent requests a resource and gets a 402 with `accepts`, a list of `PaymentRequirements`.
2. The agent picks one and sends its signer a Writ call, op `x402/pay`, whose `args` carry that requirement's fields (the mapping below), under the chain of writs that gave it spending authority.
3. The signer runs spec section 7: chain, expiry, root, revocation, the bounds, replay, `count` and `total`. Only if every check passes does it sign the EIP-3009 authorization.
4. It returns the x402 `PaymentPayload` as the result body, with a tally whose `out` commits to it and whose `used.amount` is the amount it authorized. A refusal is a signed tally with a reason, and no authorization exists.
5. The agent retries its request with the payment attached, as x402 says.

This is the separation that x402Shield's design states for its own product, where the service that decides holds no signing key and the signer acts only on a permit. Here the permit is the writ chain, the decision was made when the delegator signed the writ, ahead of time and before the agent read anything untrusted (docs/where-writ-stops.md, "commit before ingest"), and anyone can check it offline.

## The mapping

| x402 field (`PaymentRequirements`) | Call argument | Bound | Notes |
|---|---|---|---|
| `amount`, a string of atomic units | `amount`, an integer | `max` per payment, `total` for the running sum at this signer | Writ integers stop at 2^53 minus 1 (spec 1.1 rule 2). The adapter refuses an `amount` that is not plain decimal digits or is larger; for a six-decimal token such as USDC the ceiling is about nine billion units of the token. |
| `payTo` | `pay_to` | `set` of allowed recipients | The bound that stops recipient substitution. EVM addresses travel in lowercase hex: Writ compares bytes and never normalizes (spec 1.1 rule 3), and EIP-55 checksum casing varies. The adapter lowercases before it signs the call and before it signs the authorization. |
| `network`, CAIP-2 | `network` | `set` | For example `["eip155:8453"]` for Base mainnet, so testnet authority cannot spend on mainnet. |
| `asset` | `asset` | `set` | The token contract, lowercase hex. |
| `scheme` | `scheme` | `set` | `["exact"]`. Under `upto`, x402's `amount` is a ceiling at verification and the settled figure at settlement, so `args.amount` is the ceiling and is what `total` reserves (spec 7.3), while `used.amount` reports what the signer authorized. |
| `maxTimeoutSeconds` | `timeout` | `max` | The signer also sets the authorization's `validBefore` no later than the leaf writ's `exp`, so an authorization never outlives the authority it was signed under. |
| `resource.url` | `host` and `path` | `set` for `host`, `prefix` for `path` | Parsed by the adapter, never prefix-matched as one string. The adapter refuses a path with a `.` or `..` segment, as writ-gate does (docs/writ-gate.md), and compares the host in lowercase. |

Two more arguments are worth carrying even without a bound:

- **`body_sha256`, the hash of the request being paid for.** The call signs it, and the tally names the call, so the receipt commits to the exact request the money bought. This is the request-to-payment binding x402Shield checks; in Writ it falls out of signing the call.
- **`method`.** A `set` bound on it keeps a payment authorized for a `GET` from being spent on a `POST`.

## An example

A team gives its research agent 50 test USDC for the day, at most 2 a payment, on the Base Sepolia testnet, to two data vendors. The network, the token, and the first recipient are the values in the x402 specification's own example; the second recipient is a placeholder.

```json
{"act":{"t":"prefix","v":"x402/pay"},
 "amount":{"t":"max","v":2000000},
 "spend":{"t":"total","v":50000000},
 "pay_to":{"t":"set","v":["0x209693bc6afc0c5328ba36faf03c514ef312287c","0x00000000000000000000000000000000000000b2"]},
 "network":{"t":"set","v":["eip155:84532"]},
 "asset":{"t":"set","v":["0x036cbd53842c5426634e7929541ec2318f3dcf7e"]},
 "scheme":{"t":"set","v":["exact"]}}
```

`amount` and `spend` name two different arguments, because a writ holds one bound per name: the adapter puts the same integer in both (`"amount": 70000, "spend": 70000`), so one call is capped at 2 USDC and the running sum at 50. The agent may narrow this writ to a sub-agent for one task, with a smaller `spend`, a single vendor, and a shorter `exp`, without asking anyone; the sub-agent's payments then draw on both totals at the signer (spec 7.3).

## What the receipts say, and what they do not

- **The tally proves the signer authorized a payment, not that it settled.** Settlement is the facilitator's, and x402's `SettlementResponse` with the transaction hash is its evidence. A deployment that wants both keeps the settlement response beside the tally; a tally can carry its hash in the result body.
- **A retry cannot become a second payment.** The call's `id` is the idempotency key (spec 7 step 9): a retried call gets the stored tally and the same `PaymentPayload`, with the same EIP-3009 nonce, so the chain refuses a second transfer even if the agent resends. EIP-3009's nonce stops replays on chain; Writ stops the signer from minting a fresh authorization for the same intent.
- **Reversal is narrow.** A settled transfer cannot be undone, so the tally's `rev` is null. EIP-3009 defines an optional `cancelAuthorization`; where the token implements it, a signer may promise to cancel an authorization that has not settled, set `rev.until` to its `validBefore`, and serve `sys/undo` by calling it. Where the token does not, `rev` stays null.
- **Totals are per signer.** An agent with two signers has two running sums (spec 7.3). A delegator that means one budget names one signer in `hld`.
- **Approval above a line is delegation.** A payment over the agent's `max` is refused `out_of_bounds`; a person approves it by issuing a one-use writ for that payment, at most its amount, to its recipient ([docs/approval.md](approval.md)).

## What this page is not

It is a mapping, not code. An x402 signer that speaks Writ needs EIP-712 signing with secp256k1 and Keccak-256, which the reference implementation's zero-dependency rule leaves out, so the adapter is application code around an existing wallet or signing service. The mapping is unproven against a live facilitator; the first deployment that runs it should expect to find what this page got wrong.
